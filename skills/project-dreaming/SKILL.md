# Project Dreaming

Run this workflow on an operator request or a scoped post-task review. Interactive TDD invokes it after final validation for each project and feature worked on; the autonomous orchestrator invokes it after independent review accepts a feature. A first-pass delivery and an episode without classified findings are eligible. Work one project and one feature at a time. Resolve the explicitly supplied project directory before reading or writing project records. Accept a feature node/path, episode or session ID, trace, test locator, rework entry, or hypothesis ID. If ownership is ambiguous, keep the affected analysis incomplete until it is resolved. Use [contracts](references/CONTRACTS.md) throughout, and load [paired evaluation](references/PAIRED-EVALUATION.md) when preparing or reconciling an evaluation. Resolve absolute paths only internally. Never record or report machine-specific absolute paths in learning records, evidence, receipts, handoffs, evaluation artifacts, summaries, or other persisted output. Use paths relative to the relevant project root, or relative to the orchestration workspace when identifying another project; use a project tag or stable identifier when a relative path cannot identify it. Apply this rule to quoted evidence, commands, and errors as well.

## 1. Select evidence

1. Route through the owning project's `docs/.graph.json` and the selected feature's top graph. Use exact paths and targeted search when routing is missing or stale. Verify the behavior owner, current requirements and relevant tests. When a candidate depends on a business rule or product objective, read `docs/business/intent.md` when present and the specific business document that governs the decision. Limit inspection to task sources; targeted checks of the feature and learning records may establish counterevidence or deduplicate a decision. Do not scan the entire history after each task.
2. Inspect the selected episode and related attempts in chronological order, scoped to the same project and feature. Retain each signal's originating attempt. Accept written tests, tests discarded in favor of equivalent coverage, rework changes and reviewer suggestions; classified findings are useful context, not a prerequisite. For a trace, start with metadata and outcome, then read the cited steps and underlying evidence. A session summary is a lead until checked. Do not attribute a reused session's other attempt to this episode.
3. For a direct TDD session, accept a session ID and event locator, or a project-relative test and locator with a revision or run ID when available. Reading a test and its title establishes what it checks; claiming it detected a regression also requires the corresponding execution result. If execution cannot be checked, mark its outcome unknown and use only independently verifiable facts.
4. If the evidence establishes only a factual correction, pass the claim, owner, and support directly to `project-memory`. Use `docs/adr/TESTS.md` only for an adopted project-wide convention. Route skill-level changes with representative episodes to `meta-harness`. If accessible sources do not support a testable decision, return `no_hypothesis` with the reason and inspected sources. If a necessary source or ownership cannot be inspected, return `incomplete` with the missing input and leave that scope pending.

## 2. Formulate or reconcile a hypothesis

Inspect active and archived records for the selected feature, including published rules in its document. Match the decision, condition, and exception to reuse an existing ID. Append new origins by stable locator; reprocessing the same origin is a no-op. Follow alias records to the canonical ID.

For each distinct decision, identify a verifiable observation, the situation in which a choice of test selection, ordering, or reuse could change, and a falsifiable predicted result. One episode is sufficient; material impact, recurrence, prior guidance, rework and a scheduled future task are not admission requirements. Impact may be unknown, and a first-pass success can support a candidate. A generic preference such as “write more tests”, a green test count without a concrete choice, or a duplicate observation alone does not establish a new decision. Record zero, one, or several hypotheses as the evidence supports; there is no quota. Reconcile due triggers and counterevidence on existing IDs regardless of novelty.

Write the smallest test decision the evidence motivates. State its condition, action, exception, prediction, refutation condition, and next observable trigger. Distinguish observed facts from unknown effects and predictions. A future condition is sufficient as `review_trigger`; select a distinct concrete task only when evaluation becomes possible. Use impact, recurrence, cost of error and proximity of opportunity to prioritize evaluation, not admission. A material revision preserves the old frozen text and requires a new evaluation before publishing altered guidance.

For example, if an inspected test resumes a service using the same instance while the feature requires recovery after restart, a candidate may propose testing persisted identity with a new instance on the next recovery change. Existing equivalent coverage or a same-instance-only contract is an exception; an equivalent baseline detection or redundant variant test can refute the prediction. No observed regression or future ticket is needed. Conversely, accessible sources showing only routine coverage and no distinct test choice justify `no_hypothesis`; an unreadable source needed to decide requires `incomplete`.

## 3. Prepare or reconcile an independent evaluation

Freeze the hypothesis revision, prediction, refutation, and decision criteria before receiving results. If the evaluator has selected a distinct task set, mark the revision `in_evaluation`. Give the evaluator the frozen hypothesis and the paired-run contract. The evaluator owns reserved cases, execution and verification in a separate session. Read only the returned evidence summary and its accessible verification locators when reconciling results.

Upsert the attempt by evaluation ID. Check its frozen revision, distinct task, comparability, both arms, controls, and verifier evidence before accepting its decision. For a claimed RED gain on a known failure, verify the starting-state check and the arm's actual RED result. A confirmed gain yields `validated`. Archive a refuted hypothesis with the counterexample. Keep inconclusive results active only with a concrete next trigger. A corrected hypothesis gets a new revision and a fresh evaluation.

## 4. Hand off publication or withdrawal

For a validated revision, provide the [handoff](references/CONTRACTS.md#project-memory-handoff) to the caller for its next `project-memory` invocation. In an autonomous run, stage it for phase E using the existing handoff envelope. For a direct operator request, pass it inline to `project-memory`. Include the owner, exact procedure and evidence it can inspect within its read boundary. First check whether the same ID/revision and content already resolve by graph. After the handoff, reread the feature through the graph and verify the receipt, ID, revision, content, and references. Archive as `published` only after confirmation. A failed handoff leaves `validated` in the active queue with a publication retry trigger.

On contract drift or credible counterevidence, recheck the current requirement and reconcile the same published ID. Use a withdrawal handoff for a rule that has lost support. A replacement rule needs a newly validated revision. Check that the withdrawn rule is absent through the same route before closing the transition. Preserve the original publication link, receipt, and reason in the archived record. If withdrawal is interrupted, keep a pending withdrawal with a retry trigger on that record and resolve it on re-entry.

## 5. Clean up and report

After incorporating results, revisit touched records and any due triggers in the selected feature. For a feature or release review, assess active records against their triggers and current backlog. Age and lack of a ticket prioritize inspection but do not justify deleting a verifiable origin. Use the [state rules](references/CONTRACTS.md#states-and-reconciliation) to merge duplicates, archive terminal decisions, or remove unsupported abandoned drafts. Confirm record and feature revisions before mutations, and resolve interrupted transitions by ID.

Return the [analysis receipt](references/CONTRACTS.md#analysis-receipt) for each project and feature, including inspected episodes, sources, status, IDs and dispositions or the specific reason and next action. Verify all claimed records in the owning project before reporting `recorded`. A post-task review can return no handoff. Report verified publication or withdrawal and keep unresolved evaluation or publication tied to its next trigger. Collection-only diagnosis must not evaluate, publish, or withdraw.
